# OperCerta 本地演示 JWT 与 RBAC 设计

**状态：** 已由用户确认，尚未实施  
**日期：** 2026-07-17  
**范围：** 仅 OperCerta 的 FastAPI 本地演示认证与角色边界；不接入企业 SSO/OAuth，不改变已验证的库存补货恢复、审批竞态与幂等写入语义。

## 1. 问题与目标

当前 API 将 `approver_id` 放在请求体中，只能用于本地审计字段演示，不能证明真实身份或 RBAC。该字段允许调用方冒充审批人，不能作为公开演示或后续前端的身份边界。

本次目标是在单节点本地演示范围内：

- 由服务端验证短时 JWT，并只从有效声明获得调用者身份；
- 让 `operator`、`approver`、`auditor`、`demo-admin` 有明确、可测试的职责；
- 保持健康检查公开，保护所有业务接口；
- 让审批审计使用经验证的 `sub`，不再信任请求体传入的审批人；
- 使令牌失效、伪造、缺少角色和越权具有稳定且不泄漏敏感细节的 HTTP 语义。

它不是正式账号体系、多租户隔离、密码管理或企业身份集成，不能据此声称生产级 IAM 已完成。

## 2. 已排除的替代方案

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 服务端签发并校验本地短时 JWT | 采用 | 与详细设计的 demo token 接口一致；身份、角色和审批审计可由自动化测试证明。 |
| 静态 API Key | 不采用 | 难以表达谁做了审批，不能自然覆盖角色边界。 |
| OAuth/OIDC/企业 SSO | 暂不采用 | 需要外部身份提供商、回调地址、密钥轮换和公开部署配置，超出当前已确认范围。 |

## 3. 身份与权限矩阵

| 角色 | 创建补货 operation | 查看 operation | 提交审批 | 演示令牌管理/评测 |
| --- | --- | --- | --- | --- |
| `operator` | 允许 | 允许 | 拒绝（403） | 拒绝（403） |
| `approver` | 拒绝（403） | 允许 | 允许 | 拒绝（403） |
| `auditor` | 拒绝（403） | 允许 | 拒绝（403） | 拒绝（403） |
| `demo-admin` | 拒绝（403） | 允许 | 拒绝（403） | 作为后续评测入口预留；本轮不新增管理写接口 |

所有角色均只能处理合成演示数据。首版不做数据行级隔离；这一限制必须在公开演示与 README 中保留，不能将 RBAC 误述为多租户权限系统。

## 4. JWT 契约

JWT 使用受维护库实现的 HS256 签名。设置模型新增且只从环境变量读取：

- `OPERCERTA_JWT_SIGNING_KEY`：必填 `SecretStr`，不写入日志、响应、测试快照或 Git；
- `OPERCERTA_JWT_ISSUER`：固定签发方；
- `OPERCERTA_JWT_AUDIENCE`：固定受众；
- `OPERCERTA_JWT_TTL_SECONDS`：正整数、短时有效期；
- `OPERCERTA_DEMO_TOKEN_ENABLED`：本地演示令牌入口开关，默认关闭。

每个成功签发的令牌至少包含 `sub`、`role`、`iss`、`aud`、`iat`、`exp` 和唯一 `jti`。服务端同时验证签名、算法、签发方、受众、时间声明和角色枚举；不接受客户端以自定义声明扩展权限。

`POST /api/v1/auth/demo-token` 只在显式启用的本地演示环境可用。其职责仅为取得受配置限制的演示令牌，不代表账号注册、登录或生产认证。公开部署时该入口默认关闭并返回稳定的不可用错误；不以“隐藏 URL”替代身份安全。

## 5. API 与错误语义

- `/health/live` 与 `/health/ready` 保持公开，供容器编排健康探针调用。
- 其余 `/api/v1/*` 业务路径需要 `Authorization: Bearer <JWT>`。
- 缺失、格式错误、签名无效、过期、受众或签发方不符的令牌统一返回 `401` 与稳定错误码 `authentication_required` 或 `invalid_access_token`，不回显验证失败细节。
- 身份有效但无所需角色返回 `403` 与 `permission_denied`。
- 审批请求体删除 `approver_id`；`BoundApprovalCommand.approver_id` 由验证后的 JWT `sub` 注入。原有六项 approval binding 与 `decision`、`reason` 保持不变。
- 认证/授权失败发生在业务 runner、审批 Repository 与 MCP 调用之前，因此不会生成审批、工单或业务审计写入。

## 6. 审计、恢复与兼容性约束

审批已落库后仍沿用既有原子事务：一个 operation 最多一个审批决定，状态先到 `resuming`，恢复协调器随后按原决定继续。JWT 只决定“谁能提交”和“以谁的身份记录”，不参与恢复时重新授权，也不写入 LangGraph checkpoint。

身份本身不进入 operation 请求体、证据内容、模型上下文或日志正文。现有审批记录中的 `approver_id` 字段继续保存经验证的主体字符串，便于审计回读；它不保存原始 JWT。

## 7. TDD 验收标准

先写并观察 RED，再实现最小代码使其 GREEN。至少覆盖：

1. 健康探针无需令牌，业务接口缺令牌返回 401 且零业务写入；
2. 有效 `operator` 可创建和查看，但不能审批；
3. 有效 `approver` 可查看和审批；请求体不能再指定或伪造 `approver_id`；
4. 有效 `auditor`、`demo-admin` 仅可读取当前已公开的 operation 信息；
5. 过期、篡改、错误签发方、错误受众和未知角色均被拒绝；
6. 并发审批仍只有一条审批记录和至多一条工单；
7. 认证后的批准、拒绝和重启恢复继续满足既有数据库断言。

完成后才可更新本地质量门禁与 Docker smoke 脚本的认证调用方式。公开部署、SSO、前端登录页、SSE 和多租户隔离仍是后续独立范围，发布门禁保持关闭。
