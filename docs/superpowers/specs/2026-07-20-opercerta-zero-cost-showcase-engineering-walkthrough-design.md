# OperCerta 零成本求职展示与本地工程拆解设计规格

**日期：** 2026-07-20
**状态：** 已完成对话确认，待用户复核书面规格
**范围：** 仅 OperCerta 静态专题、本地工程拆解页及个人作品集中的 OperCerta 状态；不启动 ForenTrail、SiteVerum 或 Federune。

## 1. 背景与决策

OperCerta 已完成库存补货、设备维修、作业异常恢复三条本地业务闭环，以及固定评测、Redis/OpenTelemetry、真实模型代表性验证、React 控制台、WSL2/Docker Compose 和 GitHub Actions 阶段证据。当前公开资源为：

- 个人作品集：<https://kxh-agent-portfolio.netlify.app>
- OperCerta 静态专题：<https://opercerta-kxh.netlify.app>
- Public GitHub：<https://github.com/KXHXK/opercerta>

用户在公网方案中选择“方案 A：零成本求职展示”。本阶段不购买 VPS，不把可写 FastAPI、MCP、PostgreSQL 或模型密钥暴露到公网；HR 访问必须即时、稳定、无冷启动。完整真实后端继续通过本地 Compose 用于学习、面试现场和后续录屏。

本规格替代旧公开专题中已经过期的 `Mock 模型`、设备场景未完成、真实模型待执行等当前状态，但保留旧规格和证据作为历史演进记录。

## 2. 目标与非目标

### 2.1 目标

1. 让 HR 在约 30 秒浏览中理解项目解决的问题、三业务范围、技术栈和实际完成度。
2. 让技术面试官继续向下查看架构、可靠性机制、真实模型、测试证据和故障案例。
3. 提供一个仅本地可见的“工程拆解”界面，使用户能沿真实请求链路掌握业务流程、源码、测试、技术效果和面试表达。
4. 公开页保持专业、自然、具有个人编辑风格，不表现为教程、模板站或自动生成页面。
5. 继续只使用公开或合成数据，不引入任何旧公司材料，不虚构指标。

### 2.2 非目标

- 不提供公开可写 Agent 后端、公开演示 JWT、公开 MCP 或数据库访问。
- 不把静态 Netlify 部署描述为 OperCerta 生产上线。
- 不在真实视频尚未录制时放置空播放器、假进度或视频占位。
- 不在本阶段建设生产 IAM/SSO、高可用、备份恢复或收费资源。
- 不为展示效果复制第二套业务逻辑或伪造前端演示结果。
- 不启动其他三个 Agent 项目。

## 3. 核心方案：一份事实，两种阅读模式

### 3.1 公开展示模式

路由 `/` 是 Netlify 与本地均可访问的公开项目专题。它使用简洁、成熟的工程作品语言，面向 HR 和面试官，不出现学习清单、掌握进度、本地练习入口或初学者措辞。

### 3.2 本地工程拆解模式

路由 `/engineering` 只在 Vite 本地开发环境并且 hostname 为 `localhost` 或 `127.0.0.1` 时启用。生产构建访问该路径返回专业的未找到页或回到公开专题；公开导航不显示入口。

页面名称统一使用“工程拆解 / Engineering Walkthrough”“实施证据”“故障复盘”，不使用“小白、入门、初学、跟着做、学习中”等措辞。掌握进度只保存在浏览器 `localStorage`，不上传、不进入公开页面。

### 3.3 共享事实源

公开页和本地页共用类型化的项目事实清单，包括：

- 三业务名称、对象类型、工具、规则摘要和工单类型；
- 已验证测试数量与验证日期；
- 当前真实模型供应商、模型名和代表性运行边界；
- GitHub 证据路径、源码路径与发布门禁状态。

工程拆解内容可以比公开摘要更详细，但不能维护一份相互矛盾的重复指标。所有数字必须来自现有证据文件；实现后如测试数量变化，先更新证据再更新页面。

## 4. 视觉语言与人工编辑感

### 4.1 视觉方向

采用“运营工程档案”风格，而不是通用 SaaS 模板：

- 基底：暖白、纸灰、深墨蓝；
- 库存：青绿色；
- 设备：琥珀色；
- 作业：紫蓝色；
- 风险和关闭门禁：低饱和红棕；
- 使用细线、编号、状态标识、时间线和真实界面截图形成个性。

标题桌面端控制在约 48px 以内，移动端约 34px；不使用占满首屏的超大字、巨型渐变球、连续发光卡片或整页深色面板。卡片不全部使用相同圆角和等高结构，允许有节制的不对称编辑布局，但阅读顺序必须明确。

### 4.2 禁止的生成归因和模板味

公开 UI 与页面 metadata 不出现以下归因：

- “AI 生成”“由 AI 创建”“Codex 生成”“Built with Codex”；
- 自动生成模板水印、模型徽标或生成过程说明。

“AI Agent”仍可用于准确描述项目类型和目标岗位；禁止的是生成归因，不是项目领域名称。

文案使用具体工程事实，避免“重新定义未来”“革命性体验”“赋能一切”等空泛口号。每项技术必须连接实际职责、源码或证据。

### 4.3 动效与流畅性

允许的动效：

- 场景颜色和边框在 hover/focus 时轻微变化；
- 流程节点展开时使用短时 `opacity`/`transform`；
- 进入视口时对重点区块执行一次轻量淡入；
- 数字和状态切换使用短时过渡。

禁止的交互：

- `position: fixed` 或 sticky 的大侧栏、悬浮卡片和遮挡内容的固定模块；
- scroll snap、强制整屏翻页、横向拖拽 carousel；
- 无限循环动画、视差背景、Canvas 粒子、自动播放视频；
- 对 width、height、top、left 等触发布局的连续动画；
- 为视觉效果引入大型动画库。

所有动效支持 `prefers-reduced-motion`；关键内容在 JavaScript 或动画失败时仍按正常文档流显示。图片声明宽高并延迟加载非首屏资源，首屏不加载视频或远程媒体。

## 5. 公开展示页信息架构

公开页是一个连续纵向页面。导航使用正常文档流中的紧凑目录，点击后平滑滚动但不把 `#projects` 等 hash 写进 URL；不使用分页和固定悬浮导航。

### 5.1 Hero：30 秒判断

- 标题：OperCerta 与一句业务价值；
- 三业务一句话：库存不足、设备告警、作业阻塞进入受控处置；
- 四个已验证事实：3 条业务闭环、42 条固定评测、6 次真实模型代表操作、最新完整后端测试数量；
- 两个外链：GitHub 源码、个人作品集；
- 明确标签：静态项目专题、公开源代码、生产门禁关闭。

Hero 不提供“在线运行”“创建工单”或会误导为公网后端的按钮。

### 5.2 三业务闭环

每个场景展示对象、异常、决策、审批和工单：

| 场景 | 状态工具 | 确定性规则摘要 | 工单类型 |
| --- | --- | --- | --- |
| 库存不足 → 补货 | `inventory.get_snapshot` | 可用库存低于补货点；目标差额受最小/最大订货量约束 | `replenishment` |
| 设备告警 → 维修 | `equipment.get_status` | 心跳过期、设备状态或允许告警级别触发；规则映射优先级 | `repair` |
| 作业阻塞 → 恢复 | `task.get_status` | blocked/overdue、重试次数和恢复策略共同决定 | `task_recovery` |

三张场景卡使用不同主题色，但共享同一视觉语法。

### 5.3 90 秒图文流程

公开流程压缩为八步：请求、鉴权校验、MCP 取证、确定性评估、模型解释、审批中断、批准后复核、幂等写入与审计。它必须明确：

- query 路径零模型、零审批、零工单；
- create path 中 Kimi 只生成 `summary`/`rationale`；
- 决策、参数、权限和写入由确定性代码、审批与数据库控制；
- 批准后绕过 Redis 重读 MCP 事实；
- LangGraph 节点可以重放，工单副作用由幂等键和唯一约束保护。

### 5.4 工程架构与可靠性

架构图展示：

```text
React -> FastAPI -> OperationRunner -> LangGraph
                                      |-> MCP/FastMCP -> 合成状态/规则/工单
                                      |-> Kimi 解释
                                      |-> Redis 只读缓存
                                      |-> PostgreSQL 业务事实/checkpoint
FastAPI -> SSE 审计回放
OpenTelemetry -> 关联 API/Graph/MCP/Redis/SQL
```

可靠性采用四个深挖入口：审批绑定、原子竞态、幂等写入、重启恢复。公开页给出简洁说明和 GitHub 证据链接，不展开成教学步骤。

### 5.5 真实证据与故障案例

首版使用：

- `console-approval-flow.png`：本地合成数据等待审批；
- `console-audit-flow.png`：本地审计序列至 completed；
- 三业务固定评测、缓存矩阵、真实模型代表性验证的事实摘要；
- 三个真实调试案例：时间派生字段进入审批哈希、Caddy 路由被 SPA fallback 吞掉、旧 Compose 镜像导致指标矛盾。

截图必须标明“本地合成数据运行证据”。后续只有用户亲手复现并确认后，才增加设备/作业截图和 3–5 分钟视频。

### 5.6 边界与联系

页尾明确区分：

- 已验证：本地三业务、真实模型代表性运行、固定评测、Compose 重启恢复、静态公网展示；
- 未完成：生产 IAM/SSO、公开可写 HTTPS 后端、限流/防滥用、高可用、Release Tag；
- 静态 Netlify 页面不是生产业务后端。

保留 GitHub、作品集和邮箱入口；不在 OperCerta 专题重复显示电话号码，电话号码继续留在个人作品集联系区。

## 6. 本地工程拆解页

工程拆解页不使用固定侧栏。顶部提供普通文档流目录，后续按章节折叠；移动端保持单列，不产生横向滚动。

### 6.1 完整请求链路

十个可选择步骤：

1. React 选择角色、场景和动作；
2. FastAPI JWT/RBAC 与 Pydantic 校验；
3. PostgreSQL 创建 operation 与审计；
4. LangGraph 进入对应场景图；
5. Redis miss/hit 与六个 MCP 工具；
6. 确定性 assessment/plan 与 Kimi 解释边界；
7. approval binding、checkpoint 与 interrupt；
8. PostgreSQL 行锁原子审批；
9. checkpoint 恢复、无缓存复核和 snapshot mismatch；
10. `work_order.create`、`work_order.get`、终态审计与 SSE。

每一步使用同一结构：为什么需要、源码入口、输入输出、数据库变化、实际效果、失败行为、自动化证据、面试追问。

### 6.2 三业务矩阵

工程拆解页除公开摘要外，继续展示：

- 合成对象 ID 与证据类型；
- 初始 MCP 工具和规则工具；
- 核心领域评估条件；
- 类型化 approval parameters；
- 工单 payload 判别字段；
- query/create、拒绝、过期、事实变化和未知对象路径；
- 场景共享内核与类型化隔离的原因。

### 6.3 技术栈效果映射

| 技术 | 项目中的实际职责 | 必须展示的验证效果 |
| --- | --- | --- |
| React | 场景、角色、详情、审批和审计 UI | 三业务同页、公开页零 API、移动布局 |
| FastAPI/Pydantic | HTTP、认证、严格输入、错误 envelope、lifespan | 非法输入零 operation，角色权限不可伪造 |
| LangGraph | 状态机、interrupt、checkpoint、恢复 | A/B 重启后保持等待审批并继续执行 |
| MCP/FastMCP | 六个白名单工具与结构化边界 | 真实独立服务、双向校验、写后读 |
| PostgreSQL | 业务真相、行锁、唯一约束、审计 | 竞态一个胜者、一个 operation 一张工单 |
| Redis | 初次/查询证据的短 TTL 缓存 | 缓存失败旁路；批准后复核不读缓存 |
| Kimi K2.6 | 严格解释字段 | 三业务 3 条真实模型路径；无权决定动作 |
| Docker Compose/Caddy | 多服务、健康、网络、入口和重启 | 仅 Caddy 暴露，API/MCP 重启恢复 |
| OpenTelemetry | 跨 API/Graph/MCP/Redis/SQL 关联 | 属性 allowlist，不记录 token/Prompt/SQL 参数 |
| GitHub Actions | 锁文件、质量、测试和 Compose 远程门禁 | PR 快速 job 与 main smoke 分层 |

### 6.4 故障复盘

至少包含：

- WSL2/Windows 组件源修复与 Docker 环境切换；
- PostgreSQL 凭据 traceback 与轮换；
- FastMCP Host 防护导致 421；
- 失败测试污染共享测试库；
- Redis/MCP 指标暴露旧镜像；
- 时间派生 heartbeat age 破坏审批哈希；
- Caddy 指令排序与非 JSON 502；
- Kimi temperature/thinking 兼容；
- 外层 10 秒与内层 30 秒的超时倒挂；
- 本地 Compose 凭据误回显后的立即轮换。

每个案例只记录观察、根因、修复、验证、限制和面试表达，不包含秘密值。

### 6.5 掌握检查

本地清单分四级：

1. 能不看稿画出链路并说明三业务差异；
2. 能亲手完成 query、创建、审批和终态查看；
3. 能制造 MCP 故障或事实变化并解释为什么零工单；
4. 能按 TDD 修改一条合成规则并解释影响范围。

四级完成前，简历使用“基于该技术完成实现并验证”，不使用无法支撑的“精通”。

## 8. 测试与验收

实现必须遵循 TDD，先写以下失败契约：

### 8.1 内容真实性

- 公开页包含三业务、六个 MCP 工具、真实模型代表性边界和最新证据。
- 不包含过期的 `Mock 模型`、设备未完成、真实模型待执行。
- 不包含生成归因或初学者措辞。
- 页面数字与证据文件一致，不出现准确率、成本、吞吐或 SLA 虚构。

### 8.2 模式隔离

- `/` 在任何主机都是公开静态专题且不调用 fetch。
- `/engineering` 仅在本地开发主机可进入。
- 生产环境 `/engineering` 不渲染掌握清单和学习导航。
- localStorage 内容不进入公开事实或网络请求。

### 8.3 业务和技术准确性

- 三业务分别映射正确工具、规则摘要和工单类型。
- query 明确零模型/零审批/零工单。
- create path 明确模型只解释、批准后无缓存复核、幂等写入。
- 十个工程步骤都有源码、测试、实际效果和失败行为。

### 8.4 体验与性能

- 390px、768px、1440px 三种视口无横向滚动和遮挡。
- CSS 不出现 `position: fixed`、强制 scroll snap 或无限动画。
- 交互支持键盘、焦点可见、图片有 alt、标题层级连续。
- `prefers-reduced-motion` 下关闭非必要动画。
- 动效只使用轻量属性；构建后记录实际 JS/CSS/图片体积，再决定是否需要压缩，不预写未测数字。
- 浏览器 console 无 error/warning；普通滚动不被脚本接管。

### 8.5 完整门禁

- 前端 focused RED/GREEN；
- 前端全量 Vitest；
- TypeScript/Vite 生产构建；
- 后端全量 pytest、Ruff、format、mypy、仓库安全扫描；
- 浏览器桌面/移动视觉检查；
- Netlify preview 的 HTML、资源指纹、截图响应和 `/api/*` 静态回退；
- preview 复核后才允许 production deploy。

## 9. 发布、回滚与后续视频

1. 本地实现公开页与工程拆解页；
2. 用户先通过 `/engineering` 学习并完成部分清单；
3. 创建 Netlify preview，验证公开页没有工程拆解入口和生成归因；
4. 固定 Git commit、记录资源指纹，替换 OperCerta production 静态专题；
5. 更新个人作品集 OperCerta 卡片：三业务与真实模型代表性验证已完成，但产品门禁仍关闭；
6. 以后用户亲手完成三业务、故障实验和讲解后，再手动提供截图并录制视频；
7. 视频文件、时长、内容和隐私通过核验后才加入公开页；
8. 回滚使用上一 Netlify production deploy，不回滚 Git 历史或删除证据。

## 10. 公网发布对话决策复盘

本节留存此前公网发布对话中的有效决策，供后续审查和优化：

1. 个人作品集和 OperCerta 专题都采用 Netlify 静态托管，保证 HR 即时打开，不依赖本机 WSL2、Docker 或后台进程。
2. 个人作品集保持一个连续页面，不使用 `/#projects` 分页式入口；四项目顺序固定为 OperCerta、ForenTrail、SiteVerum、Federune，后三项未启动。
3. OperCerta 必须先完成库存、设备、作业三业务，不再只展示库存补货。

## 11. 风险与控制

- **内容过多：** 公开页只保留摘要，深挖通过局部展开；完整工程内容只在本地页。
- **两模式漂移：** 使用共享事实清单和契约测试，不复制指标。
- **视觉过度：** 禁止重型库和持续动画，浏览器移动端实测后再调整。
- **学习内容暴露：** 生产模式禁止渲染 `/engineering`，公开导航无入口。
- **证据失效：** 发布时固定 commit 和证据日期，后续指标变化必须重新验证。
- **视频泄密：** 未经人工复核不上传；不录制终端密码、环境变量、本机路径或令牌。
- **个人掌握与自动实现混淆：** 页面区分“工程证据已完成”和“用户亲手掌握检查”，简历只写实际能解释和操作的内容。
