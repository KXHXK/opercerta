# OperCerta 开发日志与上下文恢复设计

## 目标

在同一对话自动压缩、切换会话或多人交接后，仍能从仓库中恢复 OperCerta 的已验证事实、关键决策、当前阻塞和下一步，而不依赖聊天记录或模型记忆。

日志以简体中文为主；`PostgreSQL`、`pytest`、`Git commit`、`TDD`、`FastAPI` 等专业名词保留原生英文。日志不是逐命令流水账，也不保存模型内部推理。

## 三层记录

| 层级 | 路径 | 用途 | 更新时机 |
| --- | --- | --- | --- |
| 当前状态 | `docs/development-log/current-state.md` | 当前阶段、已验证事实、阻塞、下一步和发布门禁 | 仅在命令或测试已验证后更新 |
| 每日过程 | `docs/development-log/daily/YYYY-MM-DD.md` | 当日任务、观察、动作、验证结果、失败和待办 | 每个任务检查点结束时追加 |
| 决策记录 | `docs/development-log/decisions/YYYY-MM-DD-主题.md` | 会影响架构、安全、环境、数据模型或发布门禁的选择 | 决策确定且理由可复查时创建 |

`docs/development-log/README.md` 说明模板、字段含义和恢复顺序；它属于记录机制说明，不是第四类业务日志。

## 记录边界

必须记录：

- 当前 Git branch、相关 commit、工作树状态和可回滚点。
- 已实际执行的命令类别、退出码、测试收集/通过数、版本和服务状态。
- 环境、数据库、依赖、外部 API、部署和发布门禁的关键决策。
- 失败现象、已排除原因、采用的修复、尚未解决的风险。
- 下一次会话开始前必须阅读的文件和最小下一步。

不得记录：

- 密码、API key、token、私有连接串、完整敏感请求或响应。
- 未运行命令的预期结果、未经验证的性能/质量指标，或“应该通过”之类的推测。
- 旧公司材料、内部规则、真实客户数据和与 OperCerta 无关的项目内容。
- 为凑完整性而补写的历史细节；缺少证据时应明确标为“未记录”。

## 每日条目格式

每日文件采用追加式章节，每个检查点包含：

```markdown
## HH:MM Asia/Shanghai｜任务名称

- 目标：本检查点要验证的事项。
- 观察：开始前的可复查事实。
- 动作：执行的变更或操作摘要。
- 证据：命令类别、退出码、测试结果、相关 commit 或文件路径。
- 结果：已完成、阻塞或失败；只陈述已验证事实。
- 风险与下一步：未完成项及最小下一动作。
```

涉及数据库、账户或部署凭据时，仅写“已通过本地交互式输入配置”或“已从受保护环境变量读取”，不写具体值。

## 决策条目格式

每份决策记录包含背景、候选方案、采用方案、理由、影响范围、验证方式、回滚条件和关联 commit。它不重复每日过程，只保留未来需要理解“为什么这样做”的稳定结论。

## 上下文恢复流程

自动压缩后或新会话开始时，按以下顺序读取：

1. `docs/development-log/current-state.md`
2. 最近一份 `docs/development-log/daily/` 日志
3. 与当前任务相关的 `docs/development-log/decisions/` 记录
4. `IMPLEMENTATION_HANDOFF.md`、当前实施计划和 Git 状态

若日志与测试、Git 或实际服务状态冲突，以新鲜命令输出为准，并在当日日志说明更正。

## 发布门禁关系

日志只保存门禁证据，不改变门禁。除非完整验证已在日志和发布证据文件中记录，否则 `OperCerta release gate` 保持 `CLOSED`。

## 实施范围

下一步只创建上述目录、说明、当前状态页和当天的首条日志，并将后续环境安装、TDD、测试、部署和交接按此机制记录。日志机制不引入新的运行时依赖，不改变业务代码或部署行为。
