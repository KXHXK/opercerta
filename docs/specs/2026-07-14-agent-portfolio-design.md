# AI Agent 四项目作品集组合设计

**状态：** 书面总审通过，作为后续实施基线  
**适用目标：** 上海 AI Agent / 大模型应用开发岗位  
**设计日期：** 2026-07-14  
**实施原则：** 一个项目完成、上线、复盘后，再开始下一个项目

## 1. 设计目标

本组合不是四个换皮聊天机器人，而是四类不同企业问题的可部署作品：有状态业务处置、事件驱动安全研判、多模态现场巡检、受控机器学习实验。每个项目都必须形成“输入—判断—执行或人工决定—结果回读—审计—评测”的业务闭环，同时展示不同的 Agent 框架能力。

本聊天只产出设计规格。建仓、编码、部署、评测和简历定稿在后续独立对话中按顺序完成。

## 2. 方案选择

评审过三种组织方式：

1. **四份独立规格加一份组合说明（采用）**：每个项目可独立建仓、上线和交接，组合说明负责招聘覆盖和差异化。文档数量较多，但最适合顺序开发和独立面试讲解。
2. **一份超大总体规格**：统一查看方便，但接口、状态和验收条件容易互相污染，也不利于把单个项目交给新的实施对话。
3. **四份一页项目简介**：制作快，但无法证明业务闭环、安全边界和指标口径，面试追问时支撑不足。

## 3. 设计资产

- OperCerta 详细设计：由 opercerta 独立仓库保存，使用 LangGraph 实现有状态运营处置与人工审批。
- ForenTrail 详细设计：由 forentrail 独立仓库保存，使用 CrewAI Flows 驱动安全事件证据研判。
- SiteVerum 详细设计：由 siteverum 独立仓库保存，使用 LlamaIndex Workflows 驱动多模态巡检。
- Federune 详细设计：由 federune 独立仓库保存，使用 PydanticAI 构建受控联邦实验工程平台。
- 总体设计规格：本仓库副本位于 docs/specs/ai-agent-portfolio-overall-design.md。

## 4. 四项目差异化

| 维度 | OperCerta | ForenTrail | SiteVerum | Federune |
|---|---|---|---|---|
| 企业问题 | 运营异常处置 | 安全告警研判 | 现场多模态巡检 | 联邦实验配置与复现 |
| 核心框架 | LangGraph | CrewAI Flows | LlamaIndex Workflows | PydanticAI |
| 选择理由 | 显式状态、暂停恢复、HITL | 固定 Flow 中按需组织专家角色 | 事件驱动的数据与检索工作流 | 类型化输入输出和依赖注入 |
| 主要 Agent 价值 | 将请求变成受控动作 | 多专家取证和反证 | 多模态证据融合与解释 | 自然语言转受约束实验规格 |
| 确定性核心 | 风险、规则、幂等写入 | 事件规范化、证据映射 | 视觉/几何工具、Grounding | 参数校验、训练、指标比较 |
| 人工角色 | 批准或拒绝模拟工单 | 确认结论和处置建议 | 复核报告和模拟维护任务 | 确认运行与归档结论 |
| 主要数据设施 | PostgreSQL、Redis、MCP | Kafka、OpenSearch、PostgreSQL | Milvus、MinIO、PostgreSQL | MLflow、MinIO、PostgreSQL |
| 主要性能主题 | 并行工具、缓存、恢复 | 异步解耦、批量索引、按需专家 | 裁剪图、混合检索、GPU 推理 | 客户端并行、运行复用、资源隔离 |
| 明确不做 | 多租户 ERP、真实写生产系统 | 自动封禁、真实企业日志 | 自动控制设备、医学/安全定性 | 任意代码和任意镜像执行 |

不同框架不是为了凑技术名词。四个项目分别需要状态机、角色协作、数据检索工作流和强类型 Agent，这四种主问题不同；共同的 FastAPI、PostgreSQL、React、Docker 和可观测性则体现工程方法的一致性。

## 5. 从旧材料提取什么，不提取什么

只提取通用能力：

- 仓储材料中的库位、传感、设备状态、权限和审计概念；
- 网络系统中的事件顺序、优先级、幂等消费、告警和状态追踪概念；
- 探测材料中的图片/视频输入、目标位置、轨迹、人工标注和结果文件概念；
- 联邦研究中的 Non-IID、资源约束、通信开销、可复现实验和对比分析经验。

禁止复用：原公司或课题项目名称、专有业务流程、接口路径、表结构、规则值、数据、截图、网络地址、源码结构和品牌资产。四个新仓库只使用公开或合成数据，并从零定义模型和接口。

## 6. 共同企业级基线

每个项目都必须具备：

- Pydantic 类型契约和服务边界，LLM 输出进入业务前必须二次校验；
- JWT/RBAC、输入限制、密钥管理、工具白名单和审计；
- 超时、有限重试、幂等、终态、失败分类和可恢复策略；
- 单元、集成、端到端、安全和固定评测集；
- 结构化日志、指标、Trace、健康检查和成本记录；
- Docker Compose 本地运行、CI 门禁、HTTPS 公网演示和回滚说明；
- Mock/离线模式和至少一次真实模型验证；
- README、架构图、ADR、已知限制、评测原始报告和 Release 证据。

“企业级”在这里表示边界、失败路径、权限、数据一致性和可观测性设计完整，不表示作品集已经达到多区域、高并发或大规模生产 SLA。

## 7. 指标与真实性规则

设计文档只定义测量方法和发布阈值，不预写优化百分比。任何简历数字必须能回到：

`简历描述 → release-evidence 字段 → 原始报告 → 评测脚本 → 固定数据集 → Git Commit`

对照实验必须固定数据集、并发、模型、Prompt、缓存预热和运行环境。优化多个变量时要增加中间实验，不能把组合收益归因给单一技术。目标值未达到时记录真实结果、失败样本和改进，不修改评测集迎合指标。

| Agent 编排、状态、HITL、工具调用 | OperCerta |

| Multi-Agent、事件流、模型路由、Agent 观测 | ForenTrail |
| RAG、混合检索、向量数据库、多模态、vLLM | SiteVerum |
| 类型化 Agent、评测、任务编排、ML 工程 | Federune |
| Kafka、消息幂等、DLQ、重放 | ForenTrail |
| Milvus、多向量和 Reranker | SiteVerum |
| PostgreSQL、Redis、对象存储 | 多项 |
| 受控执行、资源隔离与 Sandbox 思路 | Federune |
| Linux、Git、Docker、CI/CD、监控、安全和成本 | 四项发布链路 |

这里的“任务级记忆”不是把聊天内容永久存入向量库。OperCerta 的图状态/检查点保存当前操作上下文，ForenTrail 按案件压缩时间线，SiteVerum 只装载与当前证据相关的检索片段；状态、上下文和长期业务事实分开保存。四项都不做未经业务证明的跨用户长期人格记忆。

当前应用开发岗位的主要技术面已经覆盖：结构化模型调用、Tool Use/MCP、状态与 HITL、多 Agent、RAG/Hybrid Search/Rerank、向量数据库、多模态、模型路由/vLLM、队列与异步任务、评测/Trace/成本、安全和受控执行。覆盖目标是通用 AI Agent、LLM 应用、RAG、AI Python 后端和偏应用的 Agent 平台岗位，不是所有 AI 职位。

严重缺失但不应硬塞进首版的能力包括 Kubernetes、云厂商托管服务、大规模分布式训练、LoRA/QLoRA 微调、GraphRAG、A2A、真实多租户和企业 SSO。Coding Agent、模型算法研究、Java/Go Agent 平台也不是本组合的主证据。面对强依赖这些能力的专项岗位，应补专项学习或换项目，而不是在简历里虚构覆盖；对普通应用岗位，通过“生产演进与选型边界”说明认知即可。

## 10. 面试统一回答

### 为什么四个项目使用不同框架？

先从业务控制面选择框架，而不是先定框架再找场景。OperCerta 需要可恢复状态机和审批中断；ForenTrail 需要固定流程中按需调度专家；SiteVerum 的复杂度集中在多模态数据、检索事件和异步任务；Federune 的关键是把自然语言严格约束为可验证实验配置。若把四项都改成 LangGraph 也能实现，但会掩盖各框架的适用边界，也无法证明技术选型能力。

### 是否为了展示技术而堆栈？

每项技术都要回答“删除后哪个业务或非功能需求无法满足”。回答不出来就不进入首版。Kafka 只解决事件解耦和重放，Milvus只解决多向量检索，Redis只承担缓存、限流或短期协调；它们不是项目主角。

### 四项是否来自前公司项目？

不是。旧经历只提供了对设备状态、事件流、空间数据和联邦实验的领域理解。新项目使用合成/公开数据、全新名称、接口、表结构、规则和代码，并在仓库声明清洁室边界。

### 怎样证明不是 Demo 壳？

演示必须走到业务终态，能展示输入、结构化中间状态、证据、人工决定、执行或归档结果、失败恢复、审计记录和固定评测报告。公开 URL 只是入口，原始报告、自动化测试和可复现 Release 才是证据。

## 11. 作品集展示规则

作品集首页使用四张项目卡，但状态严格来源于 Release：

- `已上线`：在线 URL、GitHub、Release、评测报告均可访问；
- `开发中`：只显示已批准的业务目标和预计能力，不显示虚构指标或链接；
- `归档`：保留版本和限制，说明停止原因。

首轮面试优先演示 OperCerta 或 ForenTrail；SiteVerum 用于偏 RAG/多模态岗位；Federune 用于偏 Python、Agent 平台、算法工程或 MLOps 岗位。

## 12. 组合完成定义

- 四份规格之间没有名称、状态、技术栈和时间线矛盾；
- 每个项目存在明确用户、输入、输出、人工角色和全部终态；
- 每项技术有必要性、替代方案和删除条件；
- 每个指标有数据集、计算式、对照条件和证据文件设计；
- 每个项目能独立建仓、部署、上线和从作品集移除；
- 不把设计目标、计划日期和阈值写成已实现经历；
- 后续实施对话可以仅阅读对应规格和总体说明后开始制定实施计划。
