# OperCerta 学习掌握与面试训练方法

**目标：** 不把“看过文档”或“执行过命令”误认为掌握。每个技术点都要能够解释设计原因、独立复现关键行为、读懂对应代码，并诚实说明限制。

## 核心方法：读 20% → 动手 60% → 讲解 20%

### 1. 读：只读当前问题所需的最小材料

每次先选择一个主题，不从头泛读仓库。优先顺序：

1. `docs/development-log/interview-casebook.md` 的对应案例；
2. 对应的 `docs/release-evidence/` 证据；
3. 当前状态与实施计划；
4. 最小相关源码和测试。

读完后先写下预测：**它解决什么问题？如果没有它会发生什么？预期命令或测试应该看到什么？**

### 2. 动手：运行真实证据，而不是盲抄整套命令

在 WSL2 Ubuntu 中，以一个主题为单位运行基线。典型入口：

```bash
cd /mnt/d/CODEX/agent-portfolio/opercerta
sudo docker compose up --build --wait
sudo python3 scripts/verify_compose.py
```

再按主题运行精确测试，例如审批竞态、幂等工单、MCP、重启恢复或容器资产测试。命令执行前先预测结果，执行后把实际输出与预测对比。

### 3. 讲解：不用文档说清完整因果链

每次练习后用自己的话回答以下六项：

1. 用户或系统遇到了什么问题？
2. 约束是什么，为什么不能用看似简单的办法？
3. 解决方案位于 API、Workflow、MCP、数据库还是容器哪一层？
4. 用什么测试或命令证明它有效？
5. 发生故障时系统安全地做什么？
6. 当前仍有什么限制，不能夸大成什么能力？

## 安全的小实验规则

- 一次只改变一个变量；实验前确认 Git 工作树干净。
- 在新分支或临时、可恢复的改动中实验；实验结束后恢复基线。
- 不删除 PostgreSQL named volume，不修改或输出真实密码、连接串、token。
- 不把测试通过自动等同于生产通过；先确认测试覆盖的边界。
- 先观察 RED，再写最小修复并验证 GREEN；把异常输出、根因和修复记录到案例集。

## 建议学习路线

### 阶段 A：可靠性内核

主题：严格输入、数据库事务、唯一约束、审批竞态、幂等键。

完成标准：能解释“审批只接受一次”和“节点可重放但工单有效一次”的区别；能指出数据库断言位置。

### 阶段 B：可恢复工作流

主题：LangGraph 状态机、interrupt、checkpoint、业务表、RecoveryCoordinator。

完成标准：能解释为什么 checkpoint 不能代替业务数据库，以及四个重启点各自如何恢复。

### 阶段 C：服务与工具边界

主题：FastAPI 请求校验/lifespan/health，MCP 工具契约、Host 白名单、超时与安全失败。

完成标准：能画出 `API → Runner → LangGraph → MCP → PostgreSQL` 的链路，并解释 readiness 正常为何仍可能发生业务协议失败。

### 阶段 D：容器与运行环境

主题：Dockerfile、锁定依赖、Compose 依赖/healthcheck、volume、镜像 digest、网络与供应链。

完成标准：能复现 Compose smoke，并讲清 PostgreSQL 18 volume 与 registry mirror 两个真实故障的根因和边界。

### 阶段 E：完整产品门禁

主题：JWT/RBAC、SSE、React、设备场景、固定评测、安全回归、可观测性、CI/CD、HTTPS 与回滚。

完成标准：每完成一项，都有规格、RED/GREEN、自动化验证、证据、限制说明和一段面试表达；不提前声称上线。


## 后续维护规则

- 新增功能：补充“从规格到测试到源码”的学习路径。
- 新增故障：补充案例集中的问题、根因、修复、验证和限制。
- 新增术语问题：在桌面 `agent术语.md` 写简明定义，并在本文件关联到可运行的项目实验。
- 每次准备面试前：重新运行最关键的测试和 Compose smoke，只使用新鲜证据表述项目能力。
