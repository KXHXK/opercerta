# 技术复核与项目进度控制决策

日期：2026-07-16
状态：采用

## 问题

此前在每个技术规格阶段都要求用户逐段确认。用户明确指出自己无法有效判断 LangGraph、事务、类型和恢复算法等实现细节，只能形式确认。这种流程不能替代技术审查，还会增加等待和上下文切换。

同时，OperCerta 已完成较多可靠性内核工作，但尚未形成 browser → API → workflow → tool/model → structured response 的用户可见纵向闭环。若继续无限扩展底层规格，项目可能在技术局部正确的同时偏离作品集的可演示、可部署目标。

## 决策

后续采用风险分级复核：

### 需要用户决定

- 产品范围、用户体验和演示内容；
- 是否引入付费 API、外部账号或公开部署；
- 不可逆或高迁移成本的数据模型变更；
- 安全/隐私边界、发布与对外声明；
- 会明显改变时间、成本或最终目标的取舍。

### 由 Codex 负责并提供证据

- 模块拆分、类型命名、内部接口和测试夹具；
- 在已确认架构内的 Repository、LangGraph 和错误处理细节；
- 常规重构、格式化、静态类型修复和测试实现；
- 不改变产品范围的技术替代方案选择。

这些技术决定以 TDD RED/GREEN、完整测试、静态检查、Git diff、自审和开发日志负责，不再要求用户逐行判断代码或契约。只有发现范围变化、不可逆风险或多个方案会显著影响交付时才暂停询问。

## 文档分级

- A 级：数据一致性、安全、认证、外部系统、部署等高风险边界，保留书面规格；用户只看中文目标、风险和可见结果。
- B 级：已确认架构内的功能，Codex 直接编写可执行计划并实施，不重复要求技术确认。
- C 级：小型修复和机械重构，使用测试与日志记录，不单独写规格。

## 当前进度口径

百分比是规划估算，不是已测效果指标，必须同时给出分母：

- 可靠性内核：Task 1–4 已实现，Task 5 规格已确认但未实现，Task 6 未开始；考虑 Task 5 工作量较大，估算完成约 60%–65%。
- 完整 OperCerta 发布范围：已完成设计、环境和核心事务边界，但 MCP 工具、完整 workflow、API/SSE、认证、前端、固定评测、真实模型代表路径、可观测性、Docker/Linux 和公开部署尚未完成；按里程碑权重估算约 25%–30%。

可靠性内核估算采用 Task 1/2/3/4/5/6 权重 `10/10/20/20/30/10`；前四项完成得到 60%，Task 5 只完成设计约增加少量规划进度，因此给出 60%–65% 区间。完整项目估算把基础环境与设计、可靠性内核、工具/模型纵向后端、API/SSE/认证、前端、评测安全与可观测性、Docker/部署、发布材料分别作为里程碑；当前主要贡献来自前两项和部分文档，故只给 25%–30%，不按文件数或 commit 数计算。

该估算不写入简历或发布成绩，只用于排期和风险控制。

## 进度保护措施

1. Task 5 与 Task 6 完成后冻结可靠性内核，不继续增加底层框架功能。
2. 下一阶段优先建立一个可运行纵向闭环，再扩展其余 MCP 工具、UI 状态和评测。
3. 每个阶段必须产出可运行代码、测试证据和明确下一边界，不能只增加文档。
4. 每日状态记录“已验证事实、未完成范围、阻塞和下一最小步骤”。
5. 发布门禁只由完整门禁证据打开，用户的形式确认不能代替测试或部署验证。

## 时间判断

目前没有证据可以保证在一周内完成冻结详细设计中的全部公开上线范围。若外部账号、模型、托管和 Docker/Linux 环境均无阻塞，一周内完成“可靠性内核 + 本地可演示的最小纵向闭环”仍可作为进度目标；完整五工具、前端、固定评测、安全回归、真实模型样本和公开部署需要按实际门禁结果继续推进，不能为了日期删掉验证后宣称完成。
