## 问题与解决方法

### PR 后端测试缺少 vector extension

- **现象：** 后端测试不是业务断言失败，而是在迁移 `CREATE EXTENSION IF NOT EXISTS vector` 时退出。
- **根因：** 产品和本地 Compose 已使用 pgvector，但 GitHub Actions backend-tests 仍使用普通 PostgreSQL 18；代码与 CI 基础设施发生漂移。
- **修复：** 用资产契约锁定与 Compose 相同的 `pgvector/pgvector:0.8.2-pg18-trixie`，禁止回退到 `postgres:18`，再修改工作流。
- **验证：** 本地 RED/GREEN 与修复后的远程 run 同时通过。这个修复不放宽迁移、不跳过 RAG 测试，也不伪造 extension。
- **面试表达：** “本地通过而 CI 失败时，我先比较运行环境。迁移明确依赖 vector extension，根因是 CI 镜像漂移；我先写资产测试固定基础设施契约，再统一镜像并用远程 Actions 复验。”

### Kimi replan 重复已完成工具

- **现象：** 开启 RAG 后，Kimi 第一轮已取得库存和知识证据，第二轮却再次选择已完成工具，Harness 按契约返回 `duplicate_tool_call`，遗漏 policy。
- **根因：** 图虽然知道缺少哪类证据，但 replan 仍把完整工具集交给模型，给了模型重复选择的空间。
- **修复：** 根据已经持久化的 observation 计算 missing tools，下一轮只暴露尚未完成的工具；如果没有可用工具但证据仍不完整，则显式失败，不进入无界循环。
- **验证：** RED 先证明第二轮仍暴露 inventory + policy；GREEN 后 16 条定向测试通过，真实 RAG 图探针按 inventory、knowledge、policy 顺序完成。
- **面试表达：** “Harness 负责拒绝越界，Graph 负责缩小下一轮行动空间。只做重复调用拦截会让任务失败；只靠 Prompt 又不可靠，所以我同时保留硬约束并按状态裁剪工具集。”

### provider 异常后的 operation 原子收口

- **现象：** 图或 provider 在创建 operation 后抛异常时，记录可能停留在 `received`，重启恢复只能把它转成冲突失败。
- **根因：** operation 已经持久化，但图调用异常没有经过业务终态仓储。
- **修复：** runner 捕获异常后以固定安全错误写入 `failed`；收口失败时记录不含异常正文的固定日志，并重新抛出原始异常。
- **验证：** RED/GREEN 覆盖正常失败收口、provider 文本不落库、二次收口失败仍保留原始异常。

### 真实模型端到端仍受外部延迟阻塞

- **观察：** 一次完整 Compose inventory query 在约 21 秒内得到 202、`completed` operation 和 Agent Trace 200，但旧验证器只留下通用 `AssertionError`；增强安全诊断后，下一次代表调用在约 30 秒返回 `503 dependency_unavailable`。
- **判断：** 低层 native Tool Calling、无 RAG 图、修复后的有 RAG 图均已通过；最终 Compose 结果仍不是稳定成功证据。最后一次失败位于 create operation 的外部依赖有界超时，而不是数据库、MCP 健康或 operation 悬挂。
- **边界：** 不继续盲目消耗真实调用。报告只写 `create_operation / 503 / dependency_unavailable`；不能声称 Real Kimi 端到端通过，也不能用 Mock 结果替代。

### 本地测试凭据再次进入失败 traceback

- **现象：** 尝试本地完整数据库测试时，连接失败 traceback 展开了本地 PostgreSQL 测试角色凭据。
- **处置：** 该值未写入代码、Git 或文档，但必须按已暴露凭据处理；用户需在 Windows PostgreSQL 手动轮换角色密码，并同步 ignored `.env.local`。
- **后续：** 完整数据库回归由推送后的 GitHub Actions 重新执行；轮换完成前生产门禁保持关闭。文档永不记录旧值或新值。
