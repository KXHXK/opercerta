## 遇到的问题、根因与处理

### 1. Windows 挂载目录不支持 POSIX chmod

- **现象：** 生成 `.env.compose` 后执行 `chmod 600` 返回 `Operation not permitted`。
- **根因：** 仓库位于 `/mnt/d` 的 Windows NTFS/DrvFs 挂载路径，默认不完整映射 Linux POSIX 权限位。
- **处理：** 启动脚本将 chmod 失败改为显式提示，继续依赖 Windows ACL 与 Git ignore；未把密钥写入版本库。
- **经验：** 在 WSL 的 Windows 挂载目录开发时，不能把 chmod 成功当作跨平台安全门禁；秘密文件必须同时由版本控制忽略规则和宿主机访问控制保护。

### 2. Git dubious ownership

- **现象：** WSL Git 拒绝操作 Windows 所有权的仓库，并导致 `.env.compose is not ignored` 的后续误判。
- **根因：** Git 的仓库所有权保护认为 `/mnt/d/...` 与 Linux 当前用户所有权不一致。
- **处理：** 只将本项目的精确绝对路径加入全局 `safe.directory`，没有使用通配符放宽所有仓库。
- **经验：** 安全检查失败后的下游错误可能是连锁症状；应先修复最早出现的信任边界错误。

### 3. MCP 首次启动不健康

- **现象：** PostgreSQL、Redis 和 bootstrap 均成功，但 `opercerta-mcp-1` 在健康检查期内退出，API 因依赖 MCP healthy 而未启动。
- **证据：** traceback 落在 `FastEmbedGateway` 创建 `BAAI/bge-small-zh-v1.5` 的模型下载路径，最终异常为 `httpx.ConnectError: [Errno 101] Network is unreachable`。
- **根因：** Docker registry mirror 只代理容器镜像；FastEmbed 模型文件仍需单独访问 Hugging Face Hub。新机器网络无法直连该模型端点，和 MCP 协议、FastAPI 健康端点或 PostgreSQL 无关。
- **处理：** 仅在被 Git 忽略的本机 `.env.compose` 中设置 `HF_ENDPOINT=https://hf-mirror.com`，保持产品 `compose.yaml` 不硬编码第三方镜像；模型缓存继续写入命名卷 `fastembed_cache`。
- **恢复策略：** 第一次允许在线下载并填充缓存；缓存成功后可通过 `OPERCERTA_HF_HUB_OFFLINE=true` 进行离线重建验证。不能在空缓存卷上宣称离线冷启动成功。

### 4. 诊断输出不足

- **现象：** 原启动脚本失败时只显示 Compose 最终依赖错误，没有自动附带具体容器 traceback。
- **处理：** `scripts/bootstrap_project_runtime.sh` 增加 ERR trap，失败时自动输出 Compose 状态和 PostgreSQL/bootstrap/MCP/API 的尾部日志，并对常见数据库 URL 和模型 API key 进行脱敏。
