# OperCerta 开发日志：2026-07-26

## 今日目标

在继续扩展功能前，核对用户对 LLM、LangGraph、Redis 和控制台业务状态的质疑是否属于实现偏差，并形成可执行的架构纠偏规格和 TDD 计划。

## 用户复核发现

用户在本地控制台实际操作后指出：

- LLM 没有表现为观察、决策、调用工具、再观察的 Agent 大脑；
- FastAPI、LangGraph、MCP 和 Redis 的链路解释与实际代码不一致；
- 当前工具批次执行更像预设工作流，而不是真正的 ToolLoop；
- 点击一个库存 case 时其他卡片也出现响应；
- predecessor、successor 和关联 operation 被平铺，扫描后出现多张重复观感卡片；
- 多份文档链接误写成 `opercerta.worktrees`，正确根路径应为 `opercerta/.worktrees`。

这些反馈直接影响项目是否能作为 Agent 开发岗位作品展示，不能用增加 UI 文案或 Trace 标签掩盖。

## 规格核对结果

今日重新完整核对四份原始设计、2026-07-21 Agent 核心架构增强设计、signal inbox 设计、signal 对账与 successor 设计、实施交接和当前状态。

结论：用户提出的核心问题成立，而且不是临时改变需求。2026-07-21 增强设计已经明确要求 LangGraph 作为唯一编排运行时、`AgentHarness` 包含 ToolLoop、工具 Observation 返回模型后继续决策。当前代码仍采用独立 Agent 调查图、Python `ControlledActionGraph` 包装器和三个场景工作流图串联，没有完全兑现规格。

原始设计中“模型只解析意图和解释计划”的浅层边界已被 2026-07-21 增强设计修订，因此后续不能继续以原始浅层实现为理由。

## 当前实现诊断

### 后端

- FastAPI 先接收请求本身是正确的：它承担 HTTP、JWT、RBAC、Schema 和错误边界；错误在于路由/包装层过早替模型决定了工具与业务路径。
- 当前 ToolLoop 是“模型提出一批工具 → 代码全部执行 → 固定完整性检查”，工具结果没有稳定地回到模型形成多回合选择。
- Agent 调查和后续场景规则存在事实读取分叉；Redis 只包裹旧场景初读，Agent 工具路径没有统一经过缓存观察网关。
- LangGraph 被分成多个编译图再由 Python 串联，完整 operation 不由一个根图和 checkpoint 谱系拥有。

### 前端

- 浏览器复核时，一个三业务扫描结果可显示六张卡片：三条 investigating successor 和三条 attention_required predecessor。
- 后端列表返回的是开放 signal 行，前端又平铺 lineage；这不是 React key 重复，而是错误的产品读模型。
- 页面使用全局详情、Trace、事件和 busy 状态，点击一张卡片会让其他卡片产生同一响应的视觉关联。

正确模型应为：每个 `(object_type, object_id)` 一张主 case 卡片，当前 signal/operation 在卡片上，历史 signal、successor 和 operation 放入可展开谱系。

## 今日决策

1. 冻结当前待审批 operation，不继续审批或扩展功能。
2. 保留 PostgreSQL、规则、signal 认领/对账、审批竞态、绑定、幂等写入、MCP/RAG、Trace 和恢复内核。
3. 设计一个根 LangGraph 拥有完整 operation，建立有界 `model_decide ↔ execute_read_tools` 循环。
4. LLM 负责认知决策，Policy/RBAC/HITL/Verifier/事务负责最终安全与写入权威。
5. Redis 移到统一只读 Observation Gateway；扫描和批准后刷新绕过缓存。
6. 新增按业务对象聚合的 case projection 和 React case 工作台。
7. 先做库存纵向切片，通过后再复用到设备和任务。

## Task 4：批准后可靠性闭环

Task 4 先在一次性 PostgreSQL 和真实本地 MCP 上写批准/拒绝失败测试。首轮失败证明根图尚无 operation repository、审批恢复和 action gateway；补齐后，测试又真实发现两类容易被误判的工程问题：测试时钟比 MCP 证据晚十天，TTL 正确拒绝过期事实；刷新后 evidence ID 必然变化，不能仅凭 ID 变化声称业务事实漂移。

最终实现保持原事务不变量：同一个 `operation_id/thread_id` 从 LangGraph 原生 interrupt 恢复；批准后直接读取权威 MCP 并标记 cache bypass；模型 Verifier 只给认知建议，确定性 binding 比较场景、规则版本、事实哈希、计划哈希和受控参数；一致才写入，事实变化进入新审批周期，不再需要补货则终止，模型故障则失败关闭。

验证覆盖批准完成、拒绝无工单、事实漂移后二次审批、checkpoint 尚未更新但数据库已写入时的幂等回放，以及模型 Verifier 失败不能绕过写门禁。根图文件最终 `11 passed`；完整单元 `386 passed in 60.64s`；Ruff、Mypy 81 个源文件与 `git diff --check` 通过。Task 4 只完成库存候选纵向闭环，默认 API/Compose 仍未切换，下一步进入 Task 5 三场景策略泛化。未调用 Real Kimi，未 commit/push/merge，发布门禁仍为 `CLOSED`。
