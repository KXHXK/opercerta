## Task 6：Redis、OpenTelemetry 与真实模型适配器

- 先写缓存故障旁路、JSON/TTL、严格模型输出、脱敏 span、生产配置和 Redis Compose 契约测试；RED 阶段因缓存、模型和追踪模块尚不存在而在收集阶段失败，证明测试先于实现。
- Redis 只缓存初次或查询取证。缓存键带固定命名空间、证据类别和参数哈希，值保留来源/规则版本并设置短 TTL；缓存连接、解析或写入失败只记录低基数 `hit/miss/write/error`，随后直连 MCP。批准后的 `revalidate` 使用未缓存 gateway，集成测试用“初始快照不变、真实 MCP 事实变化”证明仍以 `approval_snapshot_mismatch` 安全失败。
- OpenTelemetry 默认关闭；启用时使用 OTLP HTTP exporter。API 请求、三个场景的 LangGraph 节点、MCP 读写、Redis get/set 与 SQLAlchemy 执行建立 span，API→MCP 通过 W3C trace context 传播。属性采用明确 allowlist，不记录 JWT、API key、SQL、参数、Prompt、证据正文或用户消息。
- Real model 采用 OpenAI-compatible `/chat/completions`，只接受严格 `summary`/`rationale` JSON；adapter 不强制 temperature，使用供应商默认值，超时固定且最多两次尝试。模型不能决定动作、数量、优先级或权限；真实模式失败不会切换到 Mock 后继续写入。Compose 和 CI 默认仍为 Mock。
- 官方版本复核后锁定 OpenTelemetry API/SDK/OTLP HTTP `1.44.0`；Redis 官方镜像固定为 `redis:8.8.0-trixie`，内部运行且不映射宿主机端口。Redis 镜像实际拉取和三业务 Compose 验证归 Task 7，当前不得写成已通过。
- 首次总门禁取得 `407 passed in 93.08s`，但同一命令发现两份文件需格式化，而且 `.venv\\Scripts\\python.exe -m uv` 不可用。执行 Ruff 格式化后改用全局 `uv lock --check`；最终在全部修改后的工作树重跑完整测试为 `407 passed in 102.64s`，锁文件、Ruff、131 文件格式和 mypy（62 个源文件）通过。
- 提交前安全审查发现 OpenTelemetry `start_as_current_span` 默认会把未处理异常的 message 与 stacktrace 写进 span，可能违背“无 token/正文/traceback”边界；同时指标 observer 自身异常可能让缓存旁路再次失败。新增两个 RED 用例真实复现后，Trace 改为关闭自动异常记录、只保存异常类型和 ERROR 状态，缓存指标改为完全 best-effort。Real adapter 同时加入固定 `max_tokens=256` 预算上限；修复后最终完整测试为 `409 passed in 101.15s`。
