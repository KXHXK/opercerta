# OperCerta 开发日志｜2026-07-21

## Agent 核心架构调研与设计确认

- 目标：核对当前 OperCerta 为什么表现为简易工单系统，并基于公开开源 Agent 项目补齐基础 Agent 能力，同时不破坏审批、幂等和重启恢复。
- 调研：对比 LangGraph/LangChain、LangChain Email Assistant、OpenAI Agents SDK、PydanticAI、Microsoft Agent Framework HITL、AWS Operational AI Agent、Azure Agent Starter、MCP、AG-UI、Langfuse 和 Kimi K2 Tool Calling；只借鉴通用架构，不复用项目代码、业务材料或指标。
- 发现：当前模型只生成 `summary/rationale`，MCP 由固定图节点直接调用，Prompt/Harness/RAG/Agent Trace 和完整角色 UI 不足；原详细设计的 `IntentResult`、`DecisionPlan` 和 Trace 未完整落地。
- 决策：用户批准方案 B。保留有限业务表单、单 Agent Plan-and-Execute、LangGraph 唯一编排运行时、选择性 LangChain 组件、现有可靠性内核；新增 Core LLM 目标编码/规划/分析/复核/报告、Agent Harness、受控 Tool Calling、pgvector SOP Memory、RAG 引用、Agent Trace 和 Agent 工作台。
- 安全边界：模型只提出只读工具和建议；写工具仍由审批后的确定性执行器调用。批准后模型只能 `proceed/abort/escalate`，新动作或参数必须重新审批。无自由聊天、多 Agent、任意代码执行、图像/语音、真实公司材料或隐藏思维链展示。
- 规格：`docs/superpowers/specs/2026-07-21-opercerta-agent-core-architecture-design.md`。本记录只证明设计已确认并落盘，不证明代码、pgvector、真实 Tool Calling、UI 或新测试已经完成；发布门禁保持 `CLOSED`。
- 下一步：使用 `writing-plans` 将规格拆成连续 TDD 任务，再从非法 Agent 契约、越权工具、无效 Memory、审批后参数漂移和 Trace 泄露等 RED 用例开始实施。

## 书面规格复核后的修订

- 用户确认 LangGraph 与 LangChain 不做重复编排：LangGraph 独占状态、条件边、循环、HITL 和恢复；只在有真实调用时引入 `langchain-core`/`langchain-openai` 的消息、Tool Schema、结构化输出和模型适配，不使用 `langchain.create_agent`。
- 将单向示意图改为有界循环：批准前最多重新规划一次；批准后发生事实、动作或参数变化必须进入 `needs_reapproval`，重新形成计划、binding 和审批；人工确认的脱敏记忆只影响后续 operation。
- 保留小型受控 RAG，但先完成不依赖 RAG 的 Agent Tool Loop。RAG 只检索合成 SOP/确认案例；普通检索失败显式降级，只有规则明确要求 SOP 证据时才失败关闭，绝不替代 SQL/MCP 精确事实或确定性决策。
- 官方依赖核验：保留当前 `langgraph==1.2.9`、`mcp==1.28.1`；实施时按任务直接固定 `langchain-core==1.4.9`、`langchain-openai==1.3.5`，RAG 阶段再加入 `pgvector==0.5.0`、`fastembed==0.8.0` 和 `pgvector/pgvector:0.8.2-pg18-trixie`。版本只表示当前官方可用基线，不证明兼容门禁已经通过。
- 实施计划：`docs/superpowers/plans/2026-07-21-opercerta-agent-core-architecture.md`，拆为十项 Inline TDD 任务；先完成无 RAG 的 Agent 主闭环，再接入中文 SOP RAG、Trace、前端、评测和学习交付。

- RED 1：新增测试首次收集时因 `opercerta.domain.agent`、`opercerta.agent.harness`、`prompt_registry` 不存在而失败，证明测试确实先于实现。

## Agent 核心架构 Task 2｜Kimi Tool Calling 与 LangChain adapter

- RED：先增加原生 Tool Call、未知/越权工具、严格 JSON 兼容计划、任意文本拒绝、provider 异常不降级 Mock、结构化 Goal/Analysis/Verifier/Report 和安全 probe CLI 测试；首次因上下文契约、adapter 和 probe 不存在而失败。随后补充 provider 异常脱敏测试，确认原实现会把异常继续抛到 CLI 边界后再修复。
- GREEN：新增 `AgentModelGateway` port 与 `LangChainOpenAIModelGateway`。LangChain 仅承担消息、`bind_tools`、`with_structured_output` 和 OpenAI-compatible 适配；不引入第二套 Agent Loop。模型输出继续通过 Pydantic 严格契约二次校验，未知工具、任意自然文本和无效结构全部失败关闭，Real 请求失败绝不切换 Mock。
- 供应商差异：第一次真实 `kimi-k2.6` probe 返回 HTTP 400。安全诊断没有打印响应正文；对照 Moonshot Function Calling 文档并做单变量实验后，确认领域工具名 `inventory.get_snapshot` 的点号不适合作为 provider 函数名。修复为 Gateway 边界映射：内部审计和业务契约仍使用 `inventory.get_snapshot`，wire name 使用 `inventory_get_snapshot`，避免供应商限制污染领域模型。参考：<https://platform.kimi.com/docs/api/chat>。
- 真实证据：使用仅存于被忽略 `.env.local` 的授权配置，显式关闭 thinking，固定只暴露只读库存工具。`kimi-k2.6` 成功返回原生 Tool Call，合成工具结果回传后收到 continuation；安全输出为 `planning_mode=native_tool_call`、`first_tool_name=inventory.get_snapshot`、`continuation_received=true`，本次端到端耗时 `3270 ms`。这是一次代表调用，不外推吞吐、成功率、Token 或费用指标，也不保存 Prompt/原始模型文本/密钥。
- 依赖与验证：新增直接依赖 `langchain-openai==1.3.5`，lock 解析 `99 packages`。Task 1+2 相关回归 `36 passed`，Task 2 定向 `12 passed`，Ruff 通过，mypy 对 `67 source files` 无问题，`uv lock --check` 一致。容器内没有 `uv` 可执行文件，因此 lock 检查使用已确认的 WSL `uv 0.11.28`；测试运行时仍为镜像中的 Python 3.12.13。
- 边界：本 Task 没有接入写工具、RAG 或生产 LangGraph 图；429/5xx 有限重试和 401/403 不重试由 Task 4 的单一 Harness/Graph 预算实现，当前 adapter 固定 `max_retries=0`，避免 LangChain 与 Graph 双重重试。数据库 `runtime/bootstrap.py` 不承担模型装配，生产 runtime wiring 同样延后到 Task 4。

## Agent 核心架构 Task 3｜只读 ToolPolicy 与 MCP Tool Loop

- RED：新增三场景动态工具目录、写/未知工具拦截、对象 ID 漂移、额外参数、重复调用、工具预算、成功/失败 Observation、程序缺陷不隐藏和缺失 evidence ID 拒绝测试。首次收集因 `tool_policy.py`、`tool_executor.py` 不存在而失败；补充的 evidence ID 测试也先真实失败，证明成功 Observation 不能在无证据引用时静默成立。
- GREEN：`ToolPolicy` 根据 Goal 只向 Planner 暴露当前场景事实工具与 `policy.list_constraints`，并把目标对象和 action 固定为 JSON Schema `const`。授权函数是纯函数式边界：已用调用历史由后续 LangGraph state 传入，因此重启后不会因进程内计数器丢失预算或重复调用记录。
- Tool Loop：`ToolExecutor` 只接受严格 `ToolCallProposal`，用 canonical JSON 计算 `arguments_hash`，调用 `McpToolGateway.read_agent_tool` 后生成带 `evidence_ref` 的类型化 Observation。预期业务/MCP 错误只降为固定 error code 和安全摘要；意外程序异常继续抛出，成功结果缺 UUID evidence ID 同样失败，避免“看似成功但不可审计”。
- MCP 边界：现有 FastMCP server 的三业务类型化读工具无需改写；新增 gateway 只读分派并二次校验精确参数集合。`work_order.create/get` 继续保留给审批后确定性执行路径，但既不出现在 Planner definitions，也不被 Agent read dispatcher 接受。
- 验证：Agent unit 与 MCP integration 合并回归 `51 passed`；审批竞态和幂等写入保护回归 `16 passed`；补强后 Agent unit `26 passed`。真实 MCP 测试使用 WSL2 Docker 网络中的 PostgreSQL 和临时 loopback FastMCP server，没有改写被忽略的环境文件，也没有调用真实模型。
- 下一步：完成 Ruff/mypy、安全脚本与原子提交后进入 Task 4，把 GoalEncoder→Planner→ToolPolicy→MCP Observation→Analyst→确定性 Policy Guard 接进共享 LangGraph 主循环；发布门禁保持 `CLOSED`。

## Agent 核心架构 Task 4｜共享 LangGraph 调查子图（第一增量）

- RED：新增 `test_agent_controlled_action_graph.py`，首次因共享图模块不存在而收集失败。测试参数化覆盖库存、设备和任务三场景，并要求缺少 policy 证据时最多一次 replan；随后补充 Goal 漂移和对象漂移必须在 MCP 前失败。
- GREEN：新增共享 `AgentInvestigationGraph`，节点为 `encode_goal → plan_investigation → execute_read_tools → analyze_observations`，证据不足时经 `prepare_replan` 最多回到 Planner 一次。Goal、计划、已授权调用、Observation、replan/model call 计数均为显式 JSON state，可在接入 PostgreSQL checkpointer 后参与重启恢复，而不是藏在 Python 对象成员里。
- 上下文修订：`PlanningContext` 新增 `prior_observations`，第二轮 Planner 能看到第一轮已验证结果，避免“虽然画了循环但模型不知道上一轮发生了什么”。ToolPolicy 仍拒绝重复调用、其他对象和未暴露工具。
- 安全结果：模型改写 `object_id` 返回 `trusted_goal_mismatch`；Planner 把库存对象改为 `SKU-OTHER` 返回 `object_binding_mismatch`，两者均零 MCP 调用。模型调用预算和 replan 预算由图状态显式计数，当前默认无 replan 为 3 次模型调用，有一次 replan 为 4 次。
- 新鲜验证：三业务共享图与有界 replan `6 passed`；连同 Agent、ToolPolicy 和 LangChain adapter 相关回归为 `39 passed`；Ruff/format 通过，mypy 对 `70 source files` 无问题，repository safety 通过。
- 未完成边界：本增量尚未接入现有 `ControlledActionGraph`、Operation API/数据库快照或确定性 assessment/DecisionPlan，因此不把它称为 Task 4 完成，更不改变发布门禁。下一增量先把共享调查结果转换为三业务可信 evidence，再交给现有 Policy Guard 和审批图。

## Agent 核心架构 Task 4｜确定性 Policy Guard（第二增量）

- RED：先写三业务可信字段覆盖测试，`ScenarioRegistry.evaluate_agent_result` 不存在时三条测试全部失败。测试故意让 `AgentAnalysis.recommendation` 要求“忽略规则并把数量或优先级改到最大”，用于证明模型文字不能改写业务动作参数。
- GREEN：Registry 从成功 Observation 中按工具名提取结构化 payload，重新验证为 `Inventory/Equipment/Task` 与对应 Policy evidence，并校验 Observation `evidence_ref` 必须等于 payload 的 `evidence_id`。之后复用既有 `assess_replenishment`、`assess_maintenance`、`assess_task_recovery` 和三类 plan builder。
- 可信字段结果：合成库存仍由规则计算补货量 `18`；设备 `EQ-PUMP-001` 仍计算为 `urgent`；任务仍只能选择 `manual_requeue`。模型只贡献 plan 的 `summary/rationale`，不能决定数量、优先级、恢复动作、rule version、facts hash 或 plan hash。
- 图接线：共享图在 Analyst 后新增 `calculate_policy_facts`，state 增加严格 evidence、assessment 与 `decision_plan`。Query 会完成 assessment 但不创建 plan；Create 仅在确定性 assessment 判定需要处置时生成 plan。真实 clock 作为显式依赖传入，避免隐藏当前时间导致证据 TTL 不可测。
- 新鲜验证：Policy Guard 三业务与共享图 `9 passed`；连同 Agent unit 为 `35 passed`；Ruff/format 与 mypy `70 source files` 通过。仍未接现有审批 interrupt/数据库快照，因此 Task 4 和发布门禁继续保持未完成/`CLOSED`。
