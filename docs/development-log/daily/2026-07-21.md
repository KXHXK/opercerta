# OperCerta 开发日志｜2026-07-21

## Agent 核心架构调研与设计确认

- 目标：核对当前 OperCerta 为什么表现为简易工单系统，并基于公开开源 Agent 项目补齐基础 Agent 能力，同时不破坏审批、幂等和重启恢复。
- 调研：对比 LangGraph/LangChain、LangChain Email Assistant、OpenAI Agents SDK、PydanticAI、Microsoft Agent Framework HITL、AWS Operational AI Agent、Azure Agent Starter、MCP、AG-UI、Langfuse 和 Kimi K2 Tool Calling；只借鉴通用架构，不复用项目代码、业务材料或指标。
- 发现：当前模型只生成 `summary/rationale`，MCP 由固定图节点直接调用，Prompt/Harness/RAG/Agent Trace 和完整角色 UI 不足；原详细设计的 `IntentResult`、`DecisionPlan` 和 Trace 未完整落地。
- 决策：用户批准方案 B。保留有限业务表单、单 Agent Plan-and-Execute、LangGraph 唯一编排运行时、选择性 LangChain 组件、现有可靠性内核；新增 Core LLM 目标编码/规划/分析/复核/报告、Agent Harness、受控 Tool Calling、pgvector SOP Memory、RAG 引用、Agent Trace 和 Agent 工作台。
- 安全边界：模型只提出只读工具和建议；写工具仍由审批后的确定性执行器调用。批准后模型只能 `proceed/abort/escalate`，新动作或参数必须重新审批。无自由聊天、多 Agent、任意代码执行、图像/语音、真实公司材料或隐藏思维链展示。
- 规格：`docs/superpowers/specs/2026-07-21-opercerta-agent-core-architecture-design.md`。本记录只证明设计已确认并落盘，不证明代码、pgvector、真实 Tool Calling、UI 或新测试已经完成；发布门禁保持 `CLOSED`。
- 下一步：使用 `writing-plans` 将规格拆成连续 TDD 任务，再从非法 Agent 契约、越权工具、无效 Memory、审批后参数漂移和 Trace 泄露等 RED 用例开始实施。
